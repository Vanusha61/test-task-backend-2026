# Оптимизация ночной синхронизации CRM

Точка входа: `collect_leads_customers(is_full=True)`. Формат JSONB и модель
`AbstractCustomer` сохранены; дополнительные сервисы не используются.

## Что было дорого

Для каждого покупателя и сделки выполнялись поиски в PostgreSQL по JSONB.
При отсутствии совпадения по ID добавлялся поиск по логину. Сохранение выполнялось
много раз за проход, в том числе внутри вспомогательных функций. Для 20 тысяч
покупателей и 50 тысяч сделок это десятки тысяч поисковых запросов и commit.

## Что изменено

- Существующие записи загружаются один раз в начале. Поиск по CRM ID и логину
  выполняется через словари в памяти. Логин с несколькими разными совпадениями
  не используется для сопоставления.
- Создание и обновление покупателей и сделок меняют ORM-объекты и присваивают
  новый список JSON вместо отдельного `UPDATE ... jsonb_set` для каждой сущности.
  Вспомогательные функции не выполняют commit.
- При слиянии сохраняется запись, найденная по ID сделки. Ссылки в словарях
  перенаправляются, собранные ID контактов/компаний объединяются. Индекс логинов
  покупателей пересобирается после слияния, чтобы не оставалось устаревшего `None`.
- При полном проходе очищаются отсутствующие покупатели, сделки, контакты и
  компании, а также элементы с «удалить» в имени. Пустые записи удаляются.
  Контакты и компании проверяются по связям соответствующей записи.
- Ошибки передаются наружу и вызывают rollback. Очистка после прерванной
  выгрузки не выполняется. При `is_full=False` обновления сохраняются без полной
  очистки; прежние исключения по статусам сохранены.
- В исходном конструкторе `Lead` добавлено чтение контактов из `_embedded`:
  иначе переданные контакты всегда оставались пустым списком.

## Запросы к PostgreSQL

Полный проход делает **2 SELECT**: начальную загрузку записей и итоговое чтение
для удаления пустых строк. В неполном проходе остаётся начальная загрузка.
Поисковых SELECT внутри циклов больше нет. Сохранение — один commit за успешный
проход; промежуточный flush покупателей не фиксирует транзакцию и может быть
откачен.

INSERT, UPDATE и DELETE при этом остаются: число изменяемых строк не стало
константным. Их группировка и количество обращений зависят от SQLAlchemy,
драйвера PostgreSQL и набора изменённых полей. HTTP-запросы CRM считаются отдельно.
На синтетических примерах с 5 и 50 покупателями измерено по 2 SELECT.

## Память

CRM читается итераторами, но все исходные записи БД, индексы и ID текущей выгрузки
хранятся в памяти. Расход пропорционален объёму загруженного JSON, числу
ORM-объектов, CRM ID и связей. Изменённые JSON и их прежние значения могут
одновременно удерживаться сессией до flush.

Небольшой синтетический замер: 1 000 покупателей и 2 500 сделок, примерно 1 КБ
дополнительного payload на сущность, 4,6 МБ сериализованных JSON. `tracemalloc`
показал около **27 МБ дополнительных Python-аллокаций** во время синхронизации.
Линейное масштабирование такого примера на 20 000/50 000 даёт около **550 МБ**.
Это ориентир при тех же размерах данных, не измеренный RSS полного процесса:
не учтены заранее созданные тестовые CRM-объекты, интерпретатор, нативная память
БД/драйвера. Большие `api_value`, контакты и компании увеличат расход. Полный
объём задания не запускался; для оценки рабочего RSS нужны реальные payload.

## Проверка и оставленные ограничения

В отдельном локальном стенде проверены создание/обновление, обычное и
последовательное слияние, неоднозначные логины, очистка, `is_full=False`, обрыв
выгрузки и rollback после flush/слияния. Использовались настоящие модели и
SQLAlchemy Session на временной SQLite с адаптацией DDL JSONB/BigInteger.
Это не проверка PostgreSQL JSONB-операторов, планов запросов или конкурентного
доступа. Тестовые файлы в этот репозиторий не включены.

- Предполагается, что один CRM ID покупателя не сохранён одновременно в разных
  строках БД. Для таких исходных дубликатов индекс по ID может скрыть часть
  логинов; автоматическая нормализация этих данных не реализована.
- Полноценного авторизованного клиента CRM в исходной заготовке нет. Он должен
  поставлять сущности с `get_field()`, `as_dict()`, заполненными связями и
  передавать ошибки выгрузки вызывающему коду. Боевой API не подключался.
- Точное сопоставление строк логинов сохранено без изменения регистра и
  нормализации. JSONB сохраняет ID, логины и имена для существующих поисков
  других частей системы. Новые индексы PostgreSQL и сами эти поиски не добавлялись.
- При слиянии используются полные обходы индексов и пересборка логинов. Если
  слияний много, это дополнительная Python-работа; инкрементальные индексы
  оставлены возможным дальнейшим улучшением.
- Итоговое чтение таблицы для удаления пустых записей пока сохранено ради
  простоты. Транзакция охватывает получение CRM-данных и может быть длительной
  при медленном API; параллельные запуски и блокировки отдельно не проверялись.

# Тестовое задание

Нужно ускорить ночную синхронизацию сущностей из CRM в Postgres.
Точка входа — `collect_leads_customers(is_full=True)`.
Нагрузка: 20 тыс. покупателей и 50 тыс. сделок.
Сейчас прогон делает отдельный запрос и commit на каждую сущность
и в конце ещё раз читает всю таблицу.
## Некоторые правила бизнес-логики
- Покупатель без логина пропускается.
- Покупатель ищется по id покупателя в CRM, иначе по логину среди уже сохранённых сделок.
  Если по логину нашлось больше одной записи, совпадение не используется.
- Сделка ищется по id сделки в CRM, иначе по логину среди покупателей.
  Если это две разные записи, они сливаются в ту, что нашли по сделке; вторая удаляется.
  Если не нашлось ничего, создаётся новая запись.
- После успешного полного прохода удаляются покупатели и вложенные
  сущности, которых не было в этой выгрузке, в том числе с «удалить» в имени.
- Если сбор прервался, удаление не запускается.
Падения и расхождения кода с этим списком нужно поправить.
Формат JSON в полях можно сохранить.
## Ограничения
- Python >= 3.9, Flask, SQLAlchemy, PostgreSQL.
- Celery, брокер и боевой API поднимать не нужно.
- Новые сервисы не добавлять. Схему хранения можно менять.
- Ночной прогон ищет покупателя и сделку по id CRM и по логину.
  Другие части системы ищут покупателя или сделку по точному логину и по названию.
  этот поиск писать не нужно, но выбранная схема должна его выдерживать.
  Также нужно поддерживать связь сделка-покупатель.
- Способ реализации на ваше усмотрение, правила выше обязательны.
Полный объём локально гонять не нужно: клиента CRM в репозитории нет.
Оцените память процесса и число запросов к Postgres на указанных цифрах.
